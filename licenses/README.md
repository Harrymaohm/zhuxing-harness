# 第三方依赖与许可证

本目录声明 Zhuxing Harness 使用的**全部第三方依赖及其许可证**，用于合规自查、对外交付说明与商业授权谈判。

## 为什么必须有这个目录

1. **本项目自身不是开源许可**：根目录 [LICENSE](../LICENSE) 是自定义双许可（源码可用 · 非商业免费 · 商业付费授权）。
   使用与再分发其中的第三方组件，必须满足这些组件各自的许可证条件——而我们的产物是**闭源分发**的，
   所以「保留声明」这类义务只能靠随附声明来履行。
2. **产物里查不到许可证**：打包链路（`scripts/bundle-cli.mjs` 的 esbuild、前端 Vite）会把依赖**内联**进
   `bin/harness.cjs`、`bin/kernel.mjs` 与前端 chunk。也就是说从发行物反查不出用了哪些第三方代码、
   各自什么许可——必须由本目录提供这份事实。
3. **手抄清单必然腐烂**：清单由脚本以 `pnpm licenses list` 的**实测安装结果**重新生成，不靠人工维护。

## 文件说明

| 路径 | 内容 | 维护方式 |
| --- | --- | --- |
| [THIRD-PARTY-NOTICES.md](./THIRD-PARTY-NOTICES.md) | 汇总表 + 按许可证分组的完整清单（包名、版本、作者、仓库） | **脚本生成，勿手改** |
| [texts/](./texts) | 每种许可证的代表性原文，便于随发行物一并分发 | **脚本生成，勿手改** |
| `README.md`（本文件） | 口径、义务说明、重新生成方式、已知缺口 | 人工维护 |

## 口径

- 覆盖 pnpm workspace **实际安装的全部依赖，含传递依赖与开发依赖**。
- 开发依赖不进发行物（无需随产品分发声明），但它们参与构建链路，一并列出便于完整自查。
- 各依赖的**逐包版权行**在其包内 `LICENSE` 文件里（`node_modules/<包名>/LICENSE*`）；
  `texts/` 收录的是该许可证的**代表性全文**，用于快速查阅与随包分发，署名信息以清单中的「作者」列与包内原文为准。

## 义务速查

- **需保留声明**：MIT、ISC、BSD-2/3-Clause、Apache-2.0、BlueOak-1.0.0、Python-2.0、Artistic-2.0。
- **免声明**：0BSD、CC0-1.0、MIT-0、WTFPL。
- **需评估**：MPL-2.0（弱著佐权：修改其文件需回馈）、CC-BY-3.0/4.0（署名要求，多见于数据包）。
  当前均为**未修改地作为依赖使用**，不触发额外义务；若将来修改这些包或由其代码派生，需重新评估。
- **表达式**：`(MIT OR CC0-1.0)` 这类双许可可择一遵守。

## 重新生成

```bash
node scripts/gen-licenses.mjs          # 重新生成 THIRD-PARTY-NOTICES.md 与 texts/
node scripts/gen-licenses.mjs --check  # 只校验：依赖变了却没更新声明时以非 0 退出（可接 CI）
```

**依赖有增删或升降级后必须重跑**，否则声明与实际不符——那比没有声明更糟。

## 已知缺口（尚未做，勿误以为已覆盖）

发行物**内联了依赖，但没有随包带上本目录的声明**：`scripts/build-dist.mjs` / `build-update.mjs` 的打包清单里
目前不含 `licenses/`。要真正履行「随分发物保留声明」，需要把本目录一并打进安装包与增量包
（或在校验通过的产物末尾追加 notices）。这一步会改变已产出的更新包，故未在本次一并实施。
